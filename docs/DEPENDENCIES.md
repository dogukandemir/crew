# Dependency assessment

Initial assessment: 2026-10-10; upstream advisory status rechecked 2026-10-13, including after the same-day dependency refresh (crewai 1.15.27, fastapi 0.143.0, vite 8, TypeScript 7, recharts 3). Install using `backend/uv.lock` and `frontend/package-lock.json`; avoid treating a range in a manifest as the tested version. The tested runtime is Python 3.13 and Node 26; `requires-python` is declared as `>=3.13,<3.14` because the pinned CrewAI does not support 3.14, so the manifest cannot claim a runtime the dependencies cannot run on.

The initial review found no npm audit advisories and four unique Chroma advisories (five scanner records). Those observations apply to the recorded review snapshot, not all future installs. The unused `crewai-tools` dependency was removed, including its extra document-processing dependencies. CrewAI's Anthropic extra and the directly used JSON Schema validator are now declared explicitly.

## Outstanding Chroma advisories

CrewAI 1.15.27 declares `chromadb~=1.5.9`; the lock resolves 1.5.9 (the 1.15.23 → 1.15.27 refresh moved Chroma off 1.1.1). All four advisory pages still list **no patched version** on 13 October 2026, and the advisories were introduced between 0.4.17 and 1.0.0, so every version this lock has resolved, 1.1.1 and now 1.5.9, is inside an affected range. A routine compatible version bump does not resolve these findings:

- [GHSA-f4j7-r4q5-qw2c](https://github.com/advisories/GHSA-f4j7-r4q5-qw2c): server code injection.
- [GHSA-36p7-vc44-83pf](https://github.com/advisories/GHSA-36p7-vc44-83pf): code injection.
- [GHSA-xph7-9rjv-w5fr](https://github.com/advisories/GHSA-xph7-9rjv-w5fr): authorization scope bypass.
- [GHSA-2wm9-hf6c-p5cr](https://github.com/advisories/GHSA-2wm9-hf6c-p5cr): cross-tenant access.

Crew does not ship a Chroma service or expose its server routes. CrewAI memory is disabled for worker crews; application memory uses SQLite. This limits the demonstrated exposure but **does not fix the vulnerable package** or establish that every transitive code path is unreachable. Do not start a Chroma server from this environment or expose it to untrusted callers.

Removal was tested on 13 October in a disposable, network-disabled copy of the final backend image. An import hook rejected `chromadb` before constructing a memory-disabled crew. CrewAI failed during import: `agent.core` → `base_agent_executor` → `memory.unified_memory` → `rag.embeddings.providers.openai.openai_provider` → `chromadb.utils.embedding_functions.openai_embedding_function`. Thus Chroma is an eager runtime dependency in this CrewAI version, not just an unused lockfile entry. The [uv exclusion mechanism](https://docs.astral.sh/uv/concepts/resolution/#dependency-exclusions) can omit a package but cannot repair these imports. No exclusion, fake module, unsupported override or advisory suppression was applied. A compatible upstream fix or a separately reviewed harness change is needed.

Release follow-up: rerun the advisory scan against the final lockfile; inspect CrewAI's dependency constraints for a compatible fix or removal; test the real harness after upgrading. Keep the finding open until the vulnerable dependency is removed, fixed, or a reviewed and time-bounded exception is approved by the maintainer. Do not silently ignore these advisory IDs to make CI green.

**Reviewed exception (approved by the maintainer, 13 October 2026).** The dependency workflow applies that third option, on the record: the four advisories are excepted by ID (`--ignore-vuln PYSEC-2026-311`, `-3813`, `-3814`, `-3815`) in the gated audit step, which still fails on every other finding, and a guard step fails the job the moment the locked inventory no longer pins `chromadb==1.5.9`, so the exception cannot outlive the version it was reviewed against. The raw, unfiltered scan is preserved next to the gated one (`pip-audit-raw.json` beside `pip-audit.json`) so the artifact still carries the findings even though the gate passes. Removal stays the intended resolution: re-test `import crewai.agent.core` without chromadb on every CrewAI upgrade, on 1.15.27 it still fails at `rag.embeddings.providers.openai.openai_provider` → `chromadb.utils.embedding_functions.openai_embedding_function`, exactly as the 2026-10 removal test recorded for 1.15.23.

## Outstanding mcp advisory

The 16 October 2026 inventory scan found one new advisory in the locked backend: **[CVE-2026-59951](https://github.com/advisories/GHSA-84m7-p3x7-pcfv)** (GHSA-84m7-p3x7-pcfv) in `mcp` 1.28.1, affected 1.8.0 through 1.29.1, fixed in 1.30.0 and 2.2.0. A Streamable HTTP MCP server in stateful mode never reclaimed session state: sessions did not expire, a `DELETE` ended the session but left its entry registered, and their number was unlimited. A client that could reach the endpoint could grow server memory with ordinary short requests; only a restart reclaimed it.

The package arrives transitively through CrewAI's MCP tool support: no application code imports `mcp` or starts an MCP server (checked 16 October 2026 across `backend/src` and the tests). The demonstrated path needs an MCP Streamable HTTP server reachable by callers you do not fully trust; Crew never starts one. That limits the demonstrated exposure but **does not fix the vulnerable package** or establish that every transitive code path is unreachable.

A routine bump cannot fix it: the lock resolves CrewAI 1.15.27, which declares `mcp~=1.28.1`; 1.15.28 (latest at review time, checked 16 October 2026) still does, and the fixed line starts at 1.30.0, outside that cap. Within the cap there is no patched version.

**Reviewed exception (recorded 16 October 2026; same mechanism as the Chroma exception, maintainer sign-off requested on the record).** The dependency workflow excepts the advisory by ID (`--ignore-vuln CVE-2026-59951`) in the gated audit step, which still fails on every other finding, and the guard step fails the job the moment the locked inventory no longer pins `mcp==1.28.1`, so the exception cannot outlive the version it was reviewed against. The raw, unfiltered scan still preserves the finding (`pip-audit-raw.json` beside `pip-audit.json`). Resolution: check CrewAI's `mcp` cap on every upgrade; when it admits `>=1.30.0`, adopt it and delete this exception together with the ignore flag and the guard line.

## Repeatable checks

Frontend: `npm ci` then `npm audit --audit-level=high`.

Backend: export the locked runtime dependency inventory with `uv export --frozen --no-dev --no-emit-project --format requirements-txt --output-file requirements-audit.txt`, then scan it with `pip-audit --disable-pip --require-hashes -r requirements-audit.txt`. Dependency resolution/downloads are disabled because the frozen export already lists exact versions; this is an advisory check of that inventory, not verification of installed package bytes. The security workflow keeps both reports as artifacts, the raw scan (`pip-audit-raw.json`, never gated) and the gated one (`pip-audit.json`), and fails on any finding outside the reviewed exception below. An audit service outage also requires investigation; it is not a clean scan.

The final inventory audit on 13 October completed with the same **four unique Chroma advisories (five records, including one duplicate)** and no fixed versions reported; the scanner names them `PYSEC-2026-311`, `-3813`, `-3814` and `-3815` (CVE-2026-45829/45831/45833 and the four GHSA ids above). Re-running the documented export + `pip-audit` after the 13 October dependency refresh (crewai 1.15.27, chromadb 1.5.9, 143 dependencies in the frozen inventory) reproduced exactly those five records, still with no fix versions, and the raw artifact keeps recording them after the reviewed exception: the gated run prints `No known vulnerabilities found, 5 ignored`. The frontend audit completed with **zero advisories** on both runs, including after vite 8, TypeScript 7, recharts 3 and vitest 5.0.4. A re-run on 16 October 2026 picked up the new `mcp` advisory recorded above; with both reviewed exceptions applied the gated run prints `No known vulnerabilities found, 6 ignored` (the five Chroma records above plus one mcp record). An earlier attempt using pip-based hashed collection was stopped after it stalled, then replaced with the inventory-only audit above.
